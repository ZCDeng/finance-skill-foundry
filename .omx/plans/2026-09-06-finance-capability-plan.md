# Foundry 企业财务分析能力补强方案

日期：2026-09-06。修订：r2，纳入随包财务技能的发现、加载、调用与规则迁移问题。规划模式：`$plan`。执行状态：阶段 1–7 的实现、模型评测及最终安装包状态见 [r2 验收审计](../../docs/plans/2026-09-06-finance-r2-completion-audit.md)；阶段 0 历史基线见 [r2 实施记录](../../docs/plans/2026-09-06-finance-r2-execution-log.md)。阶段 4 按用户当前条件交付适配与文件刷新，真实 ERP 联调待测试账套。本文“当前事实”和“拟新增”保留规划时基线，不能作为最新版实现状态。

## 需求摘要

面向具备专业判断能力的财务经理，保持“持续与助手讨论，同时查看结果”的统一工作区。借鉴 Datarails、Aleph、Cube 的 Excel 工作方式，Pigment、Drivetrain、Planful、Anaplan 的计划模型，以及金蝶 AI 星辰、用友体系、FineBI 的企业数据分析链路，补强 Foundry 从企业内部账套到管理报告的能力。财务分析优先，建账和资金管理保留独立领域扩展点；无需把上市公司年报检索作为主数据入口。

规划产物覆盖调研、代码差距、实施顺序与可测试验收。后续执行已由用户授权；真实 ERP 账套接入仍需要具体产品和租户条件。产品方向依据当前 `PRODUCT.md:19`、`:31`、`:39` 和已接受的 `docs/plans/2026-09-05-finance-analysis-workbench-plan.md:85`。

## 核心决策

建设一层可执行的财务语义与分析工具，贯通企业资料、计算、说明、Excel 与开放助手入口。沿用当前 Python／DuckDB／DSH／Electron，不另建一套通用 agent 平台或完整 EPM 引擎。

1. **财务经理决定口径。** 科目映射、分摊、预算口径和解释可以直接修改并生成版本；系统展示数据覆盖与计算依据，普通分析不加逐步审批。
2. **先接通已有财务技能，再沉淀高频计算。** 四项随包技能已包含报表、差异分解、对账和分录草拟的方法；先证明分析会话可发现、加载并结合现有 SQL/Python 使用，再为高频计算补充输入合同和稳定算子。保留临时问题的自由分析能力，不要求每类问题都先开发专用工具。
3. **Excel 作为工作界面之一。** 先交付可计算的文件往返，再交付真实 Excel 宿主内的范围绑定与刷新；两个等级分别验收。
4. **内部和外部助手共用计算服务。** 先扩展当前 harness 的财务工具，MCP 只是后续对外适配层。
5. **企业数据连接与计算分层。** 连接器提取数据并固化批次，runner 计算明确快照；连接凭据不进入计算脚本。当前 runner 无网络（`foundry/runner.py:39`、`:80`），需要源刷新服务来承接 ERP。

## 随包技能与新计划的分工

当前安装包 `/Applications/FA Foundry.app` 0.1.1 中核到的是四项 Anthropic `finance` 方法副本，并非完整厂商产品或已配置的 ERP 连接。方法位于应用内 Python 资源树，四项 SKILL.md 与仓库 `method/` 字节一致。核查细节与证据边界见 [技能接入补充](../../docs/research/2026-09-06-finance-capabilities/07-bundled-skills-integration.md)。

| 已有技能 | 直接复用 | 新增实施范围 |
|---|---|---|
| financial-statements | 三表结构、期间比较、差异调查与报告组织（`method/financial-statements/SKILL.md:17`） | 首期管理损益的账套映射、指标和下钻；完整法定报表后置 |
| variance-analysis | 量价分解、重要性、差异桥与说明结构（`method/variance-analysis/SKILL.md:30`、`:142`） | 可核对的算术合同、证据关联、经理编辑与重算；不用再造一套同名提示词 |
| reconciliation | 总账/明细/银行/往来核对及未达项分析（`method/reconciliation/SKILL.md:33`、`:144`） | 首期控制总额核对；后续多表匹配和账龄合同，未达项账龄不直接等同应收账龄 |
| journal-entry | 分录草拟和检查（`method/journal-entry/SKILL.md:35`、`:112`） | 保留草稿用途和未来建账扩展；不将可加载技能等同已具备过账服务 |

关系是“技能指导方法 → harness 组织调用 → Foundry 计算、保存版本和证据 → 财务经理判断与修改”。技能内容、保存后的 SQL method、专用领域算子分别承担指导、复用和稳定计算职责。

新发现的接入问题必须先解决：`dsh-plugin/package.json:139` 只是 methodSkills 声明；`foundry/harness.py:72` 只安装 preset；分析 preset 虽注册技能提供方，却未显式配置随包方法目录（`dsh-plugin/presets/analysis/agent.cordis.yml:10`）。当前宿主设置 DSH_HOME（`app/electron/harness/boot.ts:110`），不代表方法目录自动进入技能扫描范围。安装包存在、可发现、正文已加载、工具已执行四种状态分别取证。

## 财务数据与能力合同

沿用 `AnalysisStore`、dataset、revision、run、draft 与 method 的版本和正式写入机制（`foundry/analysis.py:104`、`:152`、`:217`），增加小范围领域结构；不要把新分析重新绑定到旧月结 Window。旧 `foundry/caliber.py:45`、`:267` 的科目映射及守恒规则可提取复用。

| 对象 | 最小必要内容 | 对用户的作用 |
|---|---|---|
| LedgerScope / SourceBatch | 源产品及版本、租户／账套、组织、会计日历、币种、提取时间、业务截止点、完整性、批次 ID | 知道分析的是哪本账、哪段数据以及是否完整 |
| AccountMap | 原科目代码及方向、管理科目、辅助核算映射、有效期、版本、经理调整 | 一次整理口径，后续月份复用；允许新问题临时修订 |
| FinanceFact | 分录／余额／预算／AR/AP 等类型、自然业务键、原始金额方向、原币与本位币、期间、源行定位 | 按获得的数据粒度分析；只有余额也能开始，缺少分录则说明下钻范围 |
| MetricDefinition | 表达式、维度粒度、单位、期间语义、存量/流量/比率、预算基准、有利方向、舍入与可执行转换 | 经营利润、毛利率等不再每轮从问题文本重新猜公式 |
| ScenarioRevision | 父版本、实际截止、未来期间、驱动值、依赖关系、override 与经理判断 | 比较“回款晚两周”等情景，并保留原假设 |
| ExplanationBlock | 段落、metric/run 引用、贡献明细、业务来源、经理判断、未解释余额 | 一句话下钻到计算和分录，允许经理改写 |
| WorkbookBinding | 工作簿身份、表/命名范围、输入/结果角色、指标/情景映射、上次刷新版本、冲突策略 | 原有工作簿与 Foundry 计算建立稳定关系 |

对象是建议的合同，不要求全部各建数据库或独立服务。先以现有持久记录的显式版本字段实现；跨任务共享的企业口径使用不可变配置版本，由任务引用。默认新任务仍可以直接提问、上传资料，无需先完成整套科目建模。

## 用户路径

1. 财务经理提出“本月华东利润为什么低于预算”，添加 ERP 导出的科目余额、预算和可选分录，或选择已经授权的连接。
2. 助手识别账套、期间、字段和可用明细，复用已有口径；把未映射项集中展示。资料不全时先做可完成的分析，经理可以直接修正临时口径。
3. 系统计算利润差异和贡献桥。数字说明连接到具体贡献；缺少业务原因时显示待核实解释。经理在同一工作区追问客户、部门或凭证细节。
4. 经理改分摊、预算假设或文稿，生成新版；“采用这个解释”只代表经理判断，不改变原始分录。
5. 结果送入 Excel 的指定区域或导出结果工作簿。下一次源刷新生成新批次；先显示本次变化，再更新后续分析和说明，旧成果仍可重算。

## 可选路线与选择依据

- **直接采用企业计划平台**：若已需多人预算、组织权限、流程协作和全公司模型，价值在已有成熟业务流程；代价是商业订阅、迁移和实施。Foundry 可做其分析入口，但不能从公开 API 推断已拿到完整读写能力。
- **把已有 Aleph 等作为数据中间层**：若用户已经购买并打通账套，可缩短数据整理时间；仍受支持的源系统、租户权限和工具范围影响。本轮没有这类已购事实，因此不把它写为前置依赖。
- **补强 Foundry 小型财务内核并按需接入**：最大程度复用现有版本、计算与桌面流程；代价是自行完成科目语义和连接器验证。结合当前代码和用户希望保留开放工具链的方向，建议此路线。

## 验证与完成定义

详细条件见同目录 `2026-09-06-finance-capability-test-spec.md`：34 条合同验收与至少 30 题解释评测，原 A01–A26 编号保留，新增 A27–A34 对应技能接入。阶段 0 先通过 A27–A34；其真实会话基线不依赖未来领域算子，也不冒充首期完整解释评测。阶段 1–3 保持技能回归，并通过 A01–A12、A19–A20、A22-文件、A24-内部，以及利润桥/下钻/经理改写评测子集；阶段 5 再加入账龄/现金题。A13–A18、A21、A23、A24-外部及 A26 是相应后续阶段的独立门槛，不要求首个闭环一次完成全套。A25 按阶段记录基线。先逐阶段完成新增测试，再执行现有 Python/DSH/桌面测试及 TypeScript 构建；最终真实企业样本、Excel 宿主、ERP 联调分别出证据，不相互代替。

阶段 0–3 的第一条产品闭环完成定义：安装版中的技能确实进入分析会话；经理从企业内部导出文件开始，复用/修改科目口径，生成闭合的利润差异桥，逐项下钻，编辑说明，导出可继续计算的工作簿；换一批月度资料后重跑，旧版本仍保留。阶段 4–7 是持续连接与开放入口的独立完成门槛。

本轮只完成方案文件和来源核查。没有将上述拟建文件、测试、ERP连接、Excel插件、MCP接口标为已经实现。
