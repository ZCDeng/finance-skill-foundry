# Foundry 财务解释质量补强设计 r4

状态：设计范围已补齐，实施中、尚未整体验收。基于 0.1.4 交付记录与当前代码复核；具体进度以 `2026-09-06-r4-execution-log.md` 为准。保持财务经理自由讨论、修改和保存；默认模型不变、不新增依赖。

## 目标与事实边界

原有集首轮 17/30、留出首轮 5/8 是“当前稿数值依据、任务完成度、指定下钻及正常结束”的组合成绩，不代表其余答案全是算错。最终安装版仅完成 5 题定向复测，3 题通过，不能据此推断最终版全量成绩。8 题留出集已经用于发现问题，应保留为回归集；下一轮另建未参与调优的盲测集。

本轮先解决可确定的工程缺口，再评价解释的管理价值。90% 保留为完整流程目标，不降低阈值，也不把目标写成已实现。

## r3基线复核确认的设计缺口

1. `finance_explanations.validate_explanation` 只有显式传入 `require_all_material_facts=true` 才检查重要事实覆盖，且事实来自文稿传入的 run_ids。仅开启此布尔值仍无法发现整项未运行或未选入的问题。
2. 零值主要根据列名识别，没有显式表达“利润总变动 = 各项贡献”的关系。不同结果形态可能遗漏闭合所需事实；零值、不适用和未取到数据也应分开。
3. `compute_receivables_aging` 已有截止日、活动核销与来源映射基础，但缺少争议状态筛选。模型绕行 SQL 后容易丢失币种和源行映射。F27 数值为 30，结果有 bucket、无 currency，且下钻为空。
4. 指定下钻和最多两轮修复目前主要靠生产提示执行，缺乏任务级完成记录。
5. 机器检查“pass”只覆盖已实施的检查；洞察量表尚未经财务经理标注校准。

## 设计一：把问题范围变成可检查的分析要求

在既有任务状态中增加版本化 analysis_requirements，不另建任务系统。由助手从用户请求提出范围，并由场景工具校验可执行性：目标指标、账套/组织/币种/单位、期间及比较基准、必需桥接项、用户指定下钻对象、需要回答的管理问题。

已明确的要求自动采用，工作区以一行可编辑摘要展示；只有会改变结论的歧义才在原对话中澄清。经理改范围产生新版本，旧稿标记口径已变，不能默默套用。复述问题不算证明要求正确，盲测单独检查要求提取。

要求应先于最终稿选取事实确定，不允许靠删除 run_ids 让缺项消失。工具将语义结果绑定到要求：answered / missing_data / not_applicable / pending。模型可以解释无法完成的原因，但不能自行将 missing_data 改为零。经理明确移除要求保留修订记录，不计作原问题已完成。

## 设计二：计算引擎提供完整事实组，文稿按需展开

扩展现有 prepare_explanation，返回 evidence_groups。利润桥包含总差异、收入/成本/费用贡献与残差；量价桥依据所选分解方法包含其实际定义的分项。组内成员按语义标识绑定事实 ID，不依赖 SQL 列名猜测。

每个事实区分 observed_zero、nonzero、missing、not_applicable。只有实际计算产生且来源有效的零可以作为依据；没有明细、缺一侧或模型未计算，不能补零。采用不含交互项的分解方法时，明确方法定义，不虚构一个“测得为零”的交互项。

确定性检查验证同范围同单位下的闭合关系和指定要求。正文可以只写最重要驱动，闭合零值由服务端整理为可读的“计算依据”附表，随该版本文稿保存和导出；隐藏元数据不算用户可读的依据。自动附表不覆盖经理正文，不替代正文与引用一致性检查。

保存、自动解释收尾和用户重检均调用同一检查入口。检查状态拆分为：数字与口径、要求覆盖、来源追溯；不再用一个绿色总状态暗示业务原因已经证实。普通草稿始终可保存。

## 设计三：补齐原生账龄筛选和来源链

在现有 receivables_aging 场景增加显式状态筛选，与截止日、范围、核销活动一起进入运行定义。状态映射来自数据适配与经理指定口径，不把所有企业的 active/disputed 含义写死；缺失或未知状态单列提示。

结果始终保留 ledger、organization、currency、unit、as_of、bucket 与稳定结果键；币种不混加。每个分桶可追到纳入发票及相关核销活动，同时记录剔除项目及原因。通过同一计量口径的筛选前余额 = 纳入余额 + 剔除余额进行核对；截止日后的活动不改变当期余额。历史状态不全时明确“当前状态筛选”限制，不能声称历史时点状态准确。

复用 finance_scenario_service 现有 source_rows 映射，避免先生成失去身份的临时表再凭金额反查原始发票。

SQL/Python 继续开放：可返回标准结果元数据与来源映射，服务端校验数据授权、快照、源行身份及映射适用性。源行 ID 存在不等于任意 SQL 推导已被证明；不支持的自由计算明确标记“结果可定位，源行映射未验证”，不伪造完整追溯。第一阶段只为内置场景保证完整映射。

## 设计四：让 harness 负责收尾

在现有 harness 与 FinanceService 上增加可复用的完成检查流程：计算成功 → 准备事实组 → 对指定对象取证 → 生成/更新草稿 → 检查最终版本 → 定向修复。

完成记录绑定要求版本、运行哈希、草稿版本和工具结果；调用过下钻工具不等于下钻成功，需核对返回对象和来源非空/明确无数据的状态。自然语言“请下钻利润”应命中利润对应结果，不能用收入分项替代。

确定性的引用整理和来源读取由系统完成；模型负责选重点、解释和补充判断。最多两轮模型修复，保留成功运行，按具体缺项处理。无进展、缺资料或超时即停止修复，保留可编辑成果并列明缺口。默认阈值和超时可配置，续跑以稳定操作标识避免重复保存。

此流程是分析任务的通用收尾能力，不替代自由工具探索，不要求财务经理逐步批准，不自动发布或进行账务写入。

## 设计五：围绕管理问题提高解释深度

默认呈现“结论—主要驱动—依据与判断—下一步”，不强制每次长篇报告。简短追问只回答新增问题；需要时展开完整依据。

驱动按对目标指标的绝对影响排序，突出抵消项；支持经理设置绝对金额、相对变化和特定关注对象。相对阈值必须保存分母定义，基期为零/负数时显式标记适用性，不能用不稳定百分比替代金额解释。

事实、算术驱动、业务原因假设、经理判断保持不同身份。原因有业务证据才写为已证实；缺证据时给有区分度的核查路径，例如按产品核对销量、成交价、单位成本，而非“加强管理”。行动建议关联具体发现，列出核查对象、所需资料和不同结果下的选择条件，不虚构责任人或完成时间。

经理在对话中补充“这是一次性交付”，助手可直接记为经理判断并用于适用范围，不弹新审批表；只有后来资料证实，才新增证据关联。沿用当前任务内背景版本，不贸然扩展全局记忆。

## 工作区交互

保持左侧持续讨论、右侧表格/文稿。文稿顶部展示可编辑的本次分析范围；下方以自然语言列出“金额已核对”“仍缺费用无变化的依据”“账龄来源待补齐”等具体状态。

点击金额或检查项定位到计算依据，再进入结果行、原始发票/核销记录和文件位置。缺项提供“补齐依据”“调整本次范围”“继续讨论”操作；多项同时缺失时先展示影响结论的项，避免警告堆积。经理改稿后状态及时失效，旧版本仍可查。

经理认可与机器检查分开；保留自由保存、导出及自行判断，不设计强制通过才能继续的页面。

## 设计六：统一财务输入与 Web 控件

用户补充要求：将日期、下拉等常用 Web 控件升级纳入本轮设计。沿用 Impeccable Operate 原则、现有 FA 配色及离线 Noto Sans SC。实施前，Analysis.tsx 中期间/背景生效期间为文本输入，任务、版本、资料等多处使用原生 select；本轮统一高频输入，保留整体视觉风格。共享控件现已完成安装版交互验证，具体范围见执行台账。

### 控件与财务语义

| 控件 | 行为设计 | 优先位置 |
| --- | --- | --- |
| 会计期间选择 | 年/月面板、直接键入 YYYY-MM、上期/本期快捷选择；显示实际选择值 | 分析期间、资料刷新期间、背景生效/失效期间 |
| 日期与日期范围 | 中文日历、周一开始、键入/粘贴 YYYY-MM-DD、明确清空；范围显示起止日期 | 账龄截止日、已有日期型分析参数 |
| 对比期间 | 实际期间与比较期间并列，提供上期/上年同期快捷生成，显示比较口径 | 差异分析范围摘要 |
| 可搜索单选 | 按名称/编码搜索，显示辅助信息，支持键盘选择；长名称完整可查看 | 账套、组织、资料、工作簿、任务与版本 |
| 多选筛选 | 已选项摘要、清除单项/全部、长列表搜索；“全选”明确是当前搜索结果还是全范围 | 后端已支持的状态/组织等多选条件 |
| 金额与比例输入 | 单位固定可见，失焦后格式化，编辑时保留原值；输入值以十进制字符串传递 | 重要性阈值、预算与现金情景参数 |
| 统一字段外壳 | 标签、必填/可选、说明、字段错误、禁用原因与加载状态一致 | 上述控件及现有表单 |

会计期间不转换成某天。季度、年度和非自然会计年度作为扩展能力：只有后端有明确期间集合与比较规则时开放对应选项，不能只增加一个 UI 标签。快捷“本期”优先使用当前分析口径，若使用系统日期则明确提示；不把没有资料误报为“该期间不可选”。

日期以日期字符串传输，时区仅用于事件时间；避免 Date/UTC 转换使截止日偏移一天。范围校验起始不晚于结束；不强制过去日期限制，因为预算与资金预测需要未来日期。背景的有效期间沿用期间语义。

短且固定的枚举保留统一样式的原生下拉；长列表和需要按编码查找的字段升级为可搜索选择器。可搜索不等于可任意创建：账套/资料等身份字段只能选择有效 ID；允许自定义业务背景文本的字段继续自由输入。

金额展示千分位，币种和元/万元明确；不得经过浮点转换改变精确值。比例编辑明确是百分数点还是小数比率，不能因失焦格式化而重复乘 100。未输入与 0 分开，输入未完成时不立即强制改写；粘贴存在歧义时字段旁提示。

### 连续操作与状态处理

- 日期单选确认即收起；范围选择完成两端才提交。Esc 关闭不覆盖已提交值，焦点回到触发控件；清空是明确动作。
- 支持 Tab、方向键、Enter、Esc 与中文输入法组合输入；搜索输入中的 Enter 不抢占中文候选确认。不靠鼠标 hover 才能理解选项。
- 更换账套后重新校验组织/资料等关联值；失效选项保留可见并提示重新选择，不静默替用户选第一项。
- 搜索结果区分加载中、无匹配、未配置与加载失败；异步旧结果不得覆盖用户已切换的任务/账套。大量选项采用分页或有界渲染，避免一次挂载全部。
- 只有字段提交才更新分析范围；尚未提交的日期或搜索文本不触发计算。对比较范围的更新沿用 r4 要求版本记录，不自动重跑历史结果。
- 提供就地错误说明，不把输入错误统一放进瞬时提示。机器质量告警与表单输入错误分开。

### 实现边界

在 app/src/components 中建立最小共享字段、期间/日期与选择器层，优先复用既有样式和原生能力，逐处迁移；不直接把新逻辑继续堆入 Analysis.tsx。当前依赖中无专用日期/选择控件库，本方案先定义组件行为，不预先指定或安装新依赖。若成熟组件库能明显降低键盘和日历实现成本，实施时单独提出具体依赖选择及影响；遵守新增依赖需明确请求的约定。

浮层应避免滚动容器裁剪并能贴合窗口边界翻转。Electron 中对话由独立 WebContentsView 承载，DOM portal/z-index 不能保证跨该原生视图显示；控件默认在所属工作区内展开，实际应用验证重叠、缩放、滚动与焦点，不能只以浏览器截图验收。

### 落地与验收

控件交付拆成三个可独立验收的步骤，避免把基础输入框替换当成完整交付：

1. 基础输入：共享字段、精确金额、可键入的日期/期间、可搜索单选，迁移现有高频表单。
2. 连续选择：中文日历与年月面板、日期范围、对比期间、多选筛选；接入账龄状态与分析范围版本。日期输入校验通过不等于日历交互已完成。
3. 应用联动：账套切换后的关联失效提示、异步搜索状态、键盘与中文输入法、原生窗口浮层；保存重开后期间、ID、金额必须原样往返。

典型验收任务：经理选择账套和实际/比较期间，搜索并选择资料，排除争议应收，查看剔除明细，再修改截止日。系统应保留已提交条件、明确标记旧结果口径，并允许继续讨论和保存草稿；仅输入搜索文字或尚未完成的日期不会产生新分析版本。

新增 A0 阶段：共享字段规范 → 会计期间/日期控件 → 长列表可搜索选择器。先替换分析范围、资料刷新、背景有效期以及高频资料选择，再随 A–C 阶段接入阈值、账龄筛选和版本选择。保持原字段值及已有记录兼容，不因换控件改变财务口径。

验收覆盖：闰日、跨年、月末、空值、非法输入、未来日期、期间/日期不混用；重复名称不同 ID、长中文名称、无匹配、加载失败、关联值失效、异步切换；金额精度和百分比换算；全键盘与中文输入法；系统浅/深色、窄窗、缩放、滚动浮层和原生对话视图边界。以同一任务完成选期间、选资料、改范围、保存与重开，确认值往返一致。性能预算在现有真实列表规模基线上制定，不预先声称性能提升。

| B：账龄追溯 | 状态映射与筛选、完整范围键、纳入/剔除来源 | 重复发票号、跨币种、部分核销、截止日后活动、未知状态、30/31天边界、历史状态限制；明细与汇总复算一致 |

原有30+8例保留为回归，另建并已冻结20例新盲测，覆盖持平/抵消、亏损、缺数、状态筛选、混合币种及跨期活动。真实脱敏案例可后续加入，不因暂无ERP账套阻断前三阶段。盲测中发现问题后需另留后续独立样本，避免反复调整同一套题再声称泛化。

同时报告首次完成率、两轮内完成率、延迟、工具错误与模型重试。连接错误与解释错误分开，但超时不从完整流程分母剔除。工具链数字检查、任务完成度、财务洞察分开评分。财务经理校准前不发布“专家级洞察通过率”；本方案不承诺单次运行即可达到90%。

## 扩展边界

共用任务要求、事实组、来源链和版本化判断；利润桥、账龄、13周现金分别提供领域规则。将来建账可增加借贷平衡与科目映射事实组，资金管理可增加期初余额、收付和期末余额组。分析能力可复用，但记账、付款等写入能力需单独设计授权与执行合同，不随本轮解释补强自动开放。

不采用：单纯堆长提示词；把全部数字强塞进正文；没有依据就自动补零；任意SQL自动宣称全链路可追溯；以反复重跑的最好成绩替代首轮；未经公平测试就归因于模型或更换默认模型。

## 首轮真实运行反馈：语义绑定与收尾补修

2026-09-06晚的r4/v2真实主集观察发现：对话正常结束不等于完成检查通过。F10在15次工具调用后结束，但要求覆盖与来源仍未通过；F11用了23次调用，初始要求在运行前登记，后来仅把指标表达式规范化为`revenue`，最终仍未闭合。这是中断观察中的个案诊断，不是整套质量成绩。

### 1. 要求与结果按财务语义绑定

量价桥回答收入变化，但输出列是`total_variance`、`quantity_contribution`、`price_contribution`等；当前按指标名字与列名匹配，可能把正确量价分解判成未回答。补修应复用已有事实组，给内置场景暴露受服务端约束的规范指标及成员关系：收入量价要求绑定整个量价事实组，并检查分解方法、过滤对象、期间、币种、单位和闭合状态。不能把任意含revenue字样的列当成已回答，也不能只命中一个分项就满足全部要求。

在保存要求时返回可执行的规范指标与未识别项，保留用户原问题。已知别名由确定性映射转换；不支持的表达式保留待解析状态并说明可用路径，不能先接受一个永远无法匹配的要求、再消耗模型修复次数。SQL/Python继续可用，采用显式结果合同和未验证来源标识。

### 2. 区分业务范围变更与无语义变更的规范化

F11的两版要求在问题、商品B过滤、组织、期间、币种、单位、资料和下钻要求上相同，仅把`revenue=price×quantity`改为`revenue`。简单要求最新seq必须早于run会误判这类规范化。

服务端生成要求语义指纹，运行开始时捕获并持久化实际使用的要求版本及指纹。语义等价只能来自已实现的规范化规则与相同范围/资料哈希，不接受模型自行声明“等价”。规范化修订保留版本历史，允许显式复核并复用兼容运行；改变过滤、单位、期间、分解方法、数据或删除要求，均使受影响运行失效。无法证明等价时保留重新运行路径。评分也验证这一持久化关系，不能仅靠时间顺序猜测。

### 3. 把修复建议变为可执行的下一步

完成检查返回稳定问题码、受影响要求、已有可复用运行和具体补齐动作。区分“指标合同不支持”“未运行”“未引用”“来源缺口”“旧范围”及“业务资料确实缺失”。不把工具映射缺陷交给模型反复改写正文。确定性的附表生成和来源读取自动完成，模型修复仍最多两轮；无进展明确结束为待补齐草稿，用户继续改稿和讨论不受阻。

### 验证与变更边界

增加可重现用例：收入量价要求命中完整事实组；别名规范化复用兼容运行；改商品/期间/数据源必须失效；自由声明等价被拒绝；缺数不得变零；收尾停在repair_available不能视作通过。

原观察已因可复现工程缺口中断并保存。补修使用新的实现冻结记录，评分v2保持不变；保留同源重评分与重新运行的区别，不以修改评分覆盖首轮失败。不读取独立盲测答案做定向适配。

### 扩展到比率、存量与精确修复提示

后续主集诊断将补修范围从量价推广到原生财务结果合同：

- **比率**：明确分子、分母与比率的闭合关系。分子分母保留金额单位，比率使用无量纲或百分数显示；零分母区分不适用，负分母保留定义，不能把元/万元用于比率。
- **非数值字段**：依据输出列声明类型划分数值事实与范围信息。账簿、组织、期间及展示文本不能被当成“缺失数字”；真正缺失的DECIMAL金额继续显示缺数，不能为了过检直接过滤。
- **存量科目**：通过实际运行使用的科目定义绑定金额字段，不按账套名称或资料别名猜测现金。单科目与多科目合计区分，逐期余额不跨期相加。要求中的期间集合与聚合限制需要结构化表达，正文标签不替代可执行范围。
- **精准修复**：数字标签不匹配返回对应正文片段、候选事实及语义角色，供模型局部修改；数字检查未过时，即使覆盖与来源已过，也不把completion强行标记完成。

这些是工具链合同补强，不是将所有首轮失败归因于模型。更新后仍需保持首次/修复后、完整流程/数字/管理洞察分开报告。

### 本轮实现边界与下一步

当前先落地可验证的语义匹配与明确修复动作：完整量价组、原生单科目金额、比率闭合、类型化数值事实，以及 `requirements_run_outdated`。completion policy v4 对不兼容修订返回运行ID供助手定向重算；白名单别名规范化且范围、资料和其他要求相同时，可通过服务端指纹证明复用原运行。经理仍可保留原稿。

语义指纹与等价修订复用已实现：指纹涵盖原问题、context、scope、绑定快照source/data哈希、规范化指标、维度、期间集合、下钻和移除记录，显示名称不改变计算语义。旧记录无证明时要求重新计算，不追溯补造绑定；等价编辑沿用修复预算。结构化 periods 集合已接入单科目逐期覆盖及要求编辑；不跨期合并余额。尚不提供自定义会计日历或任意场景的期间集合推导。

控件验收与解释验收独立记录：日期/期间、搜索选择、多选及字段状态已完成安装版交互检查；新的后端补修必须重新冻结、安装并按新构建验证。真实模型完整主集、留出回归与独立盲测、经理洞察校准仍是整体验收条件。

## 追加设计：避免检查器制造无效修复循环

进一步检查中断观察后，下一步重点应从单个别名扩展为可执行的结果合同。以下为新增设计；本次源码实现进度见末尾注记，安装版与真实模型验收仍单独记录。

### 结果集覆盖与支持范围

F15登记的是 `control_totals`，原生工具也完成了分币种控制合计，但要求检查不能识别该指标。应由现有原生指标/场景定义提供规范标识、支持的范围、结果成员与覆盖方式；`analysis_requirements_save` 返回可执行项和未识别项，以及可选计算路径。保留用户表述，不允许模型通过换名字或删项抹去原要求。

控制合计应绑定完整分组结果集：要求按币种列示时，覆盖所有实际返回的币种与其来源；只引用CNY一行不能满足CNY/USD结果集。单月余额只需指定期间，期间集合则逐期检查；不能把“至少找到一个同值事实”当作完整回答。基数来自受约束运行与来源范围，不由模型任意缩小。

### 缺资料时的有效答复

F12已经说明没有数量和单价，继续要求不存在的量价分解只会耗尽调用时间。增加由工具生成的能力/资料缺口记录：缺哪些列、哪个快照、哪些计算仍能完成、补什么资料后能继续。缺失证明不能仅来自正文自述。

界面分开呈现“本轮答复已结束”和“原分析要求仍有未完成项”：保留已核对的金额差异，明确量价分解待资料，不重复重建同一成功运行。缺数不记作零，不伪造完整完成率；评估另记正确说明局限的能力。

### 正文闭合式与量纲

F13正文的 `10 − 5 − 0 = 5` 是分项加总；最近的“利润”文字不应套给每个操作数。对明确、受支持的短算式执行受限语法解析与Decimal复算，再核对同一个通过闭合检查的事实组、符号、结果及完整引用；不能仅凭数字相同、出现“闭合”字样或跨组拼数放行。普通叙述继续执行标签、单位和增减方向检查。无法识别的公式明确保持未核验状态。

F15附表曾出现 `row_count: 1 元`：金额、比例、数量、条数和身份字段应分别声明量纲。条数显示“条”或无量纲，数量使用来源提供的数量单位；没有单位时明确未知，不能继承同一行金额的元/万元。格式化与引用校验必须共用语义，避免表格正确、正文或附表误标。

### 控件与分析合同的衔接

要求项的多期间选择复用会计期间控件，逐项添加和移除，保存及重新打开保留原集合。不把月份转换为日期，也不把仅编辑的期间自动提交为新分析范围。

后端支持状态使用四种明确含义：requires_execution（已识别，待计算）、requires_input（需资料或字段映射）、unrecognized（需明确计算路径）、unverified（快照未核验）。正常的待计算状态不显示缺资料。改变指标或条件后，旧支持检查不能冒充新条件的结论。

当前量价缺口证明限定于绑定快照缺少原生quantity/price默认字段；这表示需要补资料或明确字段映射，不断言其他资料不存在数量信息，也不阻止SQL/Python探索。只有全部剩余项均有工具核验缺口、数字检查通过且无其他未解决问题时，答复才结束为awaiting_input。原要求覆盖率仍保留未完成。


### 新结束状态的评分兼容

现有冻结评分v2对缺资料案例固定要求completion.status=needs_review，因此新awaiting_input不能直接算作v2通过。保留v2原观察与重评分；独立的r4/v3评分合同将工具核验的资料缺口、原要求仍未完成、明确局限、禁止继续盲目修复分别验收。不得仅扩大允许的状态集合：评分必须核对快照证据、剩余要求、最终稿哈希和数值检查。新合同测试通过后再冻结真实模型运行，避免工程状态升级被误记为模型失败或抬高旧成绩。
