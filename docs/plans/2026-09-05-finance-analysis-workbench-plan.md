# 财务分析工作台：用户流程与开放 Harness 方案

## 1. 产品方向

面向财务经理的工作台：带着问题和手头资料开始，助手读取、计算、比较、调查、生成文稿；财务经理随时修改口径和假设，检查依据，选择交付版本。方法可以在一次成功分析后沉淀，下一次复用。

核心价值是缩短“发现业务问题 → 理解原因 → 形成行动建议”的距离。可复算和版本记录服务于这个过程。用户不用先学会 skill、window、preset 或特定命令顺序。

本方案是对当前方案的产品与架构修订，尚未实现开放运行时。旧实现仍按原有约束运行。不要只删 preset 禁用项就宣称完成开放；需要一起实现调用绑定、执行记录和成果归档。

### 首先做好的五类工作

| 场景 | 用户原话示例 | 应有能力与交付 |
| --- | --- | --- |
| 经营分析 | 华东本月收入达标，利润为什么没达标？ | 实际/预算/上期数据联查，收入成本费用拆解，证据支持的解释，经营简报 |
| 预算与预测 | 回款晚两周，季度现金余额会怎样？ | 可编辑假设、情景比较、明确预测期间与余额定义，预测表 |
| 应收与回款 | 哪些客户拖累回款，先跟进谁？ | 账龄、到期日、客户/项目联查，明细下钻，跟进清单 |
| 专题分析 | 这个项目的利润是否被总部费用分摊拖低？ | 多套分摊规则并存、增量贡献与全成本对比、敏感性分析 |
| 报告与追问 | 把刚才的分析整理成会上能用的三页，再解释异常项目 | 文稿反复编辑、数字回链、同一任务内继续调查与重跑 |

先以这五类场景验证工作台，建设可组合的计算能力；不要把五类场景写成仅允许执行的菜单。月结核对保留为已有方法。

## 2. 新旧决策如何衔接

本次用户指示改变了早期产品边界。以下是明确修订，不将新要求解释成旧限制下的小幅补丁。

| 旧要求/决策 | 新决策 | 兼容方式 |
| --- | --- | --- |
| 原始 R1/R2：先授技能并跑通固定 F2 | 直接做分析；方法沉淀为可选动作 | 旧 authoring done-gate 保留给旧技能，新方法按实际声明能力及场景样例验收 |
| 原始 R3：每期先导入科目表再锁 | 可先读任意授权资料；需要正式计算时建立数据快照与口径 | 旧 Window 仍要求 CoA；新增通用 dataset，不用伪造 CoA 绕过 |
| 原始 R5：出稿前固定登记本窗问题 | 问题可增删改，分析计划可版本化 | 旧 questions.json 不重写；新增 analysis revision |
| 原始 R7、KTD7：追问限本窗且只 query-locked | 追问与初始分析具有同等研究能力，默认带上所读文稿的依据 | 显式选择比较快照，保留旧 f3 为兼容入口 |
| 9/1 KTD11：永久删除 shell/fs/jobs/delegation | 默认开放任务内文件、计算和子任务，执行环境绑定资源范围 | 开放前验证进程隔离和调用上下文，旧 preset 不原地偷偷升级 |
| 9/1 KTD12：period 禁全部 Office 工具 | 工作表草稿可创建、编辑、重算；已归档版本保持不变 | 旧只读预览继续可用，编辑发生在独立草稿区 |
| KTD2：foundry 是唯一 mutator | foundry 仍独占正式记录、快照与归档写入；harness 可写任务草稿和计算输出 | 将 canonical store 与 workspace 物理分离 |
| 一 Task 是一个结账期间 | Task 是一个业务工作目标；期间可空、可覆盖多期 | 保留既有 task id、period 和窗口链；新增字段可选 |
| 一 Window 一结论稿 | 同一数据快照可以对应多个分析、假设和文稿版本 | 旧 brief 作为 legacy deliverable，不改变历史字节 |

继续保留：数据来源快照、准确金额表示、明确口径、任务归属、交付内容哈希、历史版本、凭证草稿与正式入账的区别。移除的是不必要的流程门槛。

## 3. 财务经理的使用逻辑

### 首次打开

主入口为“开始分析”，一个问题输入框与“添加资料”。示例只帮助起步，不强制选模板。用户可以直接输入“看看这季度哪里值得关注”，助手先检查已有资料再提出分析方向。没有数据也可以先讨论口径和所需资料。

任务名由问题生成，允许修改；期间、公司、币种从资料提议，只有会实质改变计算的歧义才集中询问。缺科目表不阻止读取回款清单、预算表、合同或访谈记录。

### 完整循环

1. **提出问题、加入资料。** 表格、文档、图片或已配置的数据连接进入任务；原文件留存，解析结果与转换过程可查。
2. **先看数据再定分析。** 助手展示简短的数据摘要：期间、单位、关键字段、缺项。提出可修改的分析步骤，立即执行不依赖歧义的部分。
3. **边算边讨论。** 可查询明细、跨表联查、改分组、补数据、上网查背景、运行脚本、委派调查。用户随时改变问题，不必新建“追问座位”。
4. **调整口径和假设。** 例如“按开票口径比较”“把总部费用单独列出”“按回款率 85% 再算”。形成新 revision，旧结果与输入仍可重现。
5. **整理成果。** 从现有结果生成简报、分析工作簿、图表或行动清单。正文能表达判断、原因假说和建议，并链接支撑计算。
6. **选定版本。** 用户可以直接导出草稿；正式归档记录其选定的版本、数据依据、未解决事项及执行记录。归档后继续分析产生下一版。
7. **复用方法。** 在成功完成后选择“保存为分析方法”；保存数据契约、指标定义、步骤和输出结构，任务敏感数据与临时问题不默认进入方法。

不为读取、计划、每次计算、生成草稿逐次请求批准。用户对业务判断有决定权。计算错误、缺数据或假设未验证以具体状态表达；用户可在知情情况下保留局限并交付，系统不能将其改写为“验证通过”。

### 信息架构

- **任务**：当前分析与历史工作；新任务不要求期间。
- **任务工作区**：对话为主，旁边可切换“资料 / 分析结果 / 文稿”。资料与计算可拖入对话。
- **成果**：当前草稿、已归档版本、导出；点击数字查看来源、口径、计算与差异。
- **方法**：可选的复用库，内置方法与自己的方法都从这里进入。

“写方法 / 开始本期 / 追问”不再占据三个平行的主入口。追问是延续任务；看报告时选择“继续分析”自动带文稿版本和快照集合。Data Formulator 和 Office 成为工作区内的分析/编辑视图，用户不用管理进程或租约。

## 4. 如何开放 Harness

### 能力矩阵

| 能力 | 新分析任务默认行为 | 结果如何进入成果 |
| --- | --- | --- |
| 文件读取、搜索、OCR | 可读已加入任务的原始资料与转换结果 | 记录文件哈希、页/表/行定位；读取本身不冒充财务计算 |
| SQL、多表/跨期比较 | 在本次明确绑定的数据集合中执行 | 保存查询、参数、关系与口径检查、输出哈希 |
| Python/脚本 | 可在任务 scratch 中计算、清洗、画图 | runner 记录代码、环境、输入版本和结果；未经重跑的手填结果单独标记 |
| 表格编辑 | 可改草稿公式、假设、布局，生成新工作簿 | 区分数值手填、公式计算和引用结果；归档走 foundry |
| 网络研究 | 可用检索和受控抓取理解政策、行业和公司背景 | 来源、访问时间与发布期间分别记录；外部数字可参与计算但继承依据 |
| 子 agent / fork | 可在同一任务下拆分分析、研究、核对 | 继承 task/context 和能力上限，结果带 child run，不能改主任务快照 |
| 后台任务 | 可长时间运行分析、导出，支持取消/恢复 | 生命周期归属 task/run，重试不能重复登记交付 |
| 技能与工具扩展 | 按任务加载方法与已配置 connector | 声明输入输出、作用范围和是否有外部副作用 |
| ERP/银行等外部写入 | 作为后续领域动作单独实现 | 具体交易预览、用户提交权限、幂等与回执，不混入普通分析工具 |

“默认开放”指任务内能力开箱可用，用户不逐工具勾选。第一次把某个外部目录或数据连接加入任务时确定资源范围，后续正常操作复用。若用户主动选择更广的本机操作能力，界面说明实际范围；不能把 cwd 描述成文件系统沙箱。

### 进程与数据边界

建议结构：App → Task-aware harness → 工具路由；工具路由分别连接 foundry 正式存储服务、隔离的计算 runner、资料读取器与外部 connector。

- Harness 运行身份不能直接改 canonical store；读取通过 broker 提供的只读快照或输入副本，输出写 workspace/scratch。
- canonical store 的服务与任意脚本不能共享可写数据目录。目录命名、prompt、工具列表和 DuckDB read_only 都不能独立提供这个隔离。
- runner 的 shell 只在受控执行环境中开放：限制挂载、环境变量、网络与进程树；不把模型 provider 的宿主密钥传给计算子进程。实现时选择并验证适合桌面分发的进程隔离机制，未验证前不能宣称“任意 shell 安全开放”。
- 如果目标平台暂时无法交付隔离环境，可先用只接收输入快照、固定计算接口的 runner；界面如实展示可用能力，不删除隔离要求来伪装完成。
- SQL runner 不能直接把模型 SQL 传入现有 Window.query。只允许绑定的数据对象；禁用外部文件读取、扩展加载和任意连接；资源限额、取消与多语句处理要有真实测试。字符串前缀检查不是解析和执行隔离。
- 非确定性网络结果先固化为引用/资料版本再参与正式计算；脚本中隐式网络请求不能取得“可复算”状态。

最强反方是：放开工具会让模型产生更复杂、更难解释的错误。回应是把执行记录与业务判断分开：允许尝试，但每个正式数字都能查看依据和真实执行；“运行成功”“结果可复算”“经理认可”是三个独立状态。

### 调用绑定是前置条件

新增持久的会话上下文，服务端依据 session_id 解析 task_id、context_revision、可读 snapshot ids、workspace id、能力配置；这些字段不靠模型填，也不靠进程级 FOUNDRY_TASK 推断。

- 主会话、子 agent、fork、后台 job 使用同一个上下文注册入口。
- 改变分析快照生成新的 context revision；已启动 run 固定旧 revision，不随界面选择变化。
- current 仅为单人 CLI 交互便利；会话路径不存在 current 回退。找不到绑定时给出可恢复错误，不创建无归属窗口。
- 合法的跨期比较显式把多个快照加入本任务；不把别的任务的历史 Window 改绑到当前任务。新增 dataset binding 引用它并记录授权。
- App 对 session.create/fork 的拦截应被统一注册路径替代，注册未就绪时才继续拒绝未绑定会话。上游 session preset 的不可变性可以保留：需要更大能力时由产品创建有记录的后继会话，延续任务和上下文。

## 5. 计算、证据与用户判断

### 把问题变为可检查的分析定义

问题文本之外，AnalysisRevision 至少记录：目标指标、数据集合、维度、过滤条件、比较基准、币种/单位、期间、计算表达式、假设与关系。模型可以生成 SQL/Python，但执行前后用户都能看到“怎么算的”。普通财务经理默认看业务表达，不必读代码；展开可见完整脚本。

例如“华东实际利润对预算差异”：地区=华东，期间=2026-08，指标=利润，实际与预算分别预聚合至项目/月，按相同键关联，差异=实际−预算，差异率=(实际−预算)/预算；预算为 0 单独列示，不制造无穷大百分比。缺预算表时继续做实际分析，预算比较标缺数据。

金额以 Decimal/DECIMAL 表示并记录精度和舍入位置；统计和预测可使用浮点，但记录算法、误差/舍入及适用范围。对不同币种、存量/流量、期间和单位不静默相加。跨表先检查粒度、关联基数、重复键、未匹配行及总额变化，避免多对多重复计数。

### 最小证据结构

| 对象 | 必要内容 | 写入者 |
| --- | --- | --- |
| DatasetSnapshot | id、源版本/hash、schema、期间、单位、粒度、转换记录 | foundry |
| AnalysisRevision | 问题、表达式、snapshot bindings、假设版本、父版本 | foundry 接收用户/agent 草稿 |
| Run | id、task/session、analysis revision、实际输入、代码/参数 hash、环境、状态、输出 hash | 执行服务 |
| Claim | value/text、单位、basis、run/output 定位或来源定位、假设引用 | 成果服务根据记录生成 |
| DeliverableVersion | 内容 hash、引用的 claim/run、作者、状态、父版本 | foundry |

这五类是首阶段最小纵向链路；不先造事件总线、通用知识图谱或领域插件市场。

basis 分为来源事实、计算结果、外部引用、用户假设、专业判断。状态按四个正交字段记录：execution_status（未运行/运行中/成功/失败）、reproducibility_status（未验证/可复算/不可复算）、review_status（未阅/已阅/认可）、publication_status（草稿/归档）。不能实现成单个互斥枚举；用户已阅的失败结果也可以作为草稿导出。不能将“外部”当错误或将“已运行”当真实。

计算结果可以同时依赖账表、外部汇率和用户假设；以依赖集合表示，显示“测算，含假设”，不能因为经过 SUM 就变成无条件的账面事实。用户改数字时创建 override 版本并留下原值和说明，不能继承旧 run 的校验状态。

保留旧标签用于历史渲染。新产品不再把“稿外追问”当风险等级；“报告之后追加”只是时间关系。外部引用的 URL 与日期只证明出处已登记，不证明来源已验证。

### 正式归档检查

检查引用能否解析、执行输出是否与所引数字一致、数据版本是否存在、未完成任务是否被误写为完成。缺项可作为草稿导出或由用户带明确局限归档；伪造执行回执、修改历史字节和无权限写入不能通过。

## 6. 建账、资金管理如何扩展

公共底座保留 Task、DatasetSnapshot、AnalysisRevision/Run、Artifact/DeliverableVersion 和连接器接口。领域对象按真实业务引入，避免把所有业务都塞入 Window 状态机。

| 领域 | 可复用底座 | 独有对象及生命周期 | 建设时点 |
| --- | --- | --- | --- |
| 财务分析 | 全部 | 指标、分析口径、比较、假设、报告 | 当前主线 |
| 建账 | 资料、任务、执行、版本、人工判断 | 账套、会计期间、科目体系、期初余额、凭证；草稿→校验→过账→冲销 | 后续独立模块 |
| 资金管理 | 资料连接、情景分析、报告、审计 | 银行账户、现金头寸、收付款计划、付款指令、银行回执、对账 | 先预测/计划，后交易执行 |

分析的快照不可变不等于未来总账不能记账。未来 Ledger 是独立写模型，过账生成不可变凭证记录并投影为分析数据快照；修改通过调整/冲销而非改旧快照。分析里的管理口径调整也不自动成为凭证。

资金预测与付款执行分开：用户可自由测算延期付款、汇率与回款情景；真正发送付款指令必须通过 connector 的具体命令与回执。接受了分析结论不等于授权付款。

Connector 最小接口分为 discover/read/export 和 prepare/commit/status。首阶段只实现所需只读接入；为外部副作用预留 idempotency key、expected revision、execution receipt，不现在实现空壳 ERP 或银行业务。

## 7. 实施顺序与文件落点

| 阶段 | 可交付结果 | 主要落点 | 出口条件 |
| --- | --- | --- | --- |
| P0 纠正现有运行缺陷 | 多任务会话稳定绑定；现有汇总能力不被描述成自然语言计算引擎 | foundry/cli.py、task.py、dsh-plugin/index.js、App 会话注册 | 两任务交替与未知 session 测试；语义限制可见 |
| P1 最小开放分析闭环 | 首批支持 CSV/XLSX/表格 JSON 及 Markdown/TXT 背景资料；一任务可编辑分析与假设；受控计算有 run；文稿可修订 | 新 dataset/analysis/run 服务，工作区 UI，harness 工具注册 | 实际/预算、缺数据、非表格背景资料三类 E2E |
| P2 完整 harness 与成果 | 隔离脚本、子任务、fork/jobs、Office 草稿编辑；证据驱动归档 | runner、会话上下文、能力配置、Office adapter、deliverables | 进程隔离、取消、重跑、版本对比与真实 harness E2E |
| P3 方法复用与财务场景 | 月报、应收、情景预测；可选方法沉淀 | method、authoring、新 capability schema、fixture | 不写方法也完成首次分析；方法换数据可复用 |
| P4 领域扩展 | 建账或资金管理先选一个真实场景做纵向闭环 | 独立 ledger/treasury 模块与 connector | 各自领域不变量及外部回执验收 |

PDF/图片等资料在相应解析适配器与定位验收完成后增加，不将未支持格式悄悄丢弃或误报读完。P1 的多表比较需要声明 grain、relationship 和 metric。业务语义属于方法/分析定义，数据执行属于 runner；不要继续向 query-locked 增加针对自然语言的 if/else。

P2 才宣称完整开放 shell。P1 提供实用能力而不以一项未验证的沙箱假设阻塞所有财务分析。
